# Terrine Nonadditive Capabilities and Warehouse Scale Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add exact and explicitly approximate nonadditive dataset metrics, scalable repeated-window paths, honest runtime-plan cost estimates and budgets, and reproducible DuckDB/live-warehouse scale evidence.

**Architecture:** Extend the existing sparse temporal compiler and `compile_columns` composition instead of adding anchor-by-event fanout or dense unit-time intermediates. Keep sketches and bounded dataset contracts typed and versioned; expose estimates and unknowns through the existing metadata-only runtime planner and owner-configured executor. Build an independently generated workload and reference suite, first in local DuckDB, with live warehouse checks isolated under `integration/warehouse_execution/`.
**Tech Stack:** Python `>=3.13,<3.15` target subject to Task 0.1 compatibility evidence; existing Ibis, Arrow, Pydantic, DuckDB and pytest stack; optional sketch and warehouse-driver dependencies isolated behind explicit extras/capability checks. No network or real warehouse in unit tests.

## Global Constraints

- This task depends on Tasks 5.1 and 7.1. Implement only after the sequential/panel contracts and materialization runtime interfaces land; build on their actual merged symbols and preserve all existing callers.
- Persisted-layer composition is required to pass through `compile_design`, with substitutions propagated through shape compilation and an enumerated shape-support matrix. Unsupported shapes refuse before source work. Reuse the selector-aware invalidation contract for nested `EventTime`/`relative_to` dependencies; do not invent a second compiler or invalidation route.
- Runtime consumers MUST use Task 7.1's shared execution gate, extracted from `Frame._materialize`, for both ordinary Frame materialization and runtime staging. It audits candidate eligibility (including `unknown` refusal) and enforces required shape budgets before publication. Runtime snapshots read only the saved plan's dependency closure, not every relation in the Model/Catalog.
- Additive sparse prefix subtraction does not apply to min/max, distinct or quantile. Daily distinct counts cannot be summed; HLL sketches cannot be prefix-subtracted. Use per-kind bounded sparse/block algorithms, never unconstrained anchor × window fanout.
- Preserve exact integer/decimal values and scales where promised. Approximation must identify algorithm/version, merge operation, precision/error contract and exactness status; unsupported variants fail with a stable coded refusal and actionable route.
- `last` attributes and last-event values have different temporal contracts. Event-value ordering and ties are explicit and deterministic. Retention thresholds do not turn a completeness failure into zero/non-retention.
- Fixed winsorization bounds are explicit and transformation placement is fixed. Percentile thresholds fit on declared training rows only, are frozen for validation, test and production scoring, and use the Task 7.2 training/scoring recipe and persisted-transform lifecycle. Unsupported adapter transforms are refused, never discarded.
- Runtime planning remains metadata-only. `RefreshPlan`/`TaskSpec` uses current runtime contracts; estimated scan/output/rows remain distinct, unknown remains `None`, and output bytes never stand in for scan bytes. Forecasts, verified upper bounds and backend-enforced caps are different evidence. A strict scan budget is authorized only by a sufficient verified bound or enforceable cap covering capture, validation, execution and retries; an optimistic forecast is insufficient. No plan/run path invents an estimate or escalates a budget.
- Generator and expected-row oracle are independent of the production compiler. Keep seeded reproducibility, row-order invariance, xdist independence, and all benchmarks out of ordinary pytest unless a small fast smoke is specifically named.
- Unit tests use deterministic local fixtures only. DuckDB execution/scale evidence is explicit integration; live warehouse evidence is under `integration/warehouse_execution/`. No paid run or customer resource is authorized by this plan.
- No increment edits or mandatory increment import. Preserve explicit reviewed `__all__`, the Model/Design/Frame/Dataset workflow, numeric null reasons, coded refusals, docs/changelog, complete callsite updates, and supported-extra isolation.
- Benchmark claims report input events, anchors, emitted rows, plan/cardinality where available, client peak memory, execution scan bytes/cost, elapsed time and applicable budget. No unmeasured billion-event or universal percentage-overhead claim.

## Review Focus

1. Duplicate events, tied timestamps, and adversarial row order cause unstable last-event values or different merge results: pin deterministic typed event ordering and ties in Task 1 and Task 2.
2. Sparse windows have extreme span, sparse keys, or many anchors: pin bounded intermediates and cardinality growth without dense unit × day or anchor × raw-event intermediates in Tasks 1 and 5.
3. Empty, all-null, incomplete, and partially mature windows can look like zero distinct/retention: pin null/reason/completeness distinctions in Tasks 1 and 2.
4. Sketch merge or percentile threshold changes by batch order, package version, split boundary, or scoring run: pin exactness/error metadata, deterministic merge policy, train-only fit, and frozen thresholds in Tasks 1–2.
5. Runtime estimates are unavailable or optimistic while a strict budget is supplied: pin metadata-only unknown handling, pre-execution refusal, and separate scan/output/run/concurrency accounting in Task 5.

- Update metric/scale guides, worked examples and `CHANGELOG.md` in owning production tasks; no new parallel public root API absent a demonstrated workflow.

These are contracts to implement against the existing neighboring plans; check merged implementations before coding and revise only with coordinated caller updates.

- Public exact quantile is requested through the ordinary Design expression path: `quantile(metric: str, probability: Decimal | str, *, window: tuple[str, str], interpolation: Literal["linear_type7"] = "linear_type7") -> MetricQuantile`. The probability is canonical decimal input in `[0,1]`, never a binary float; exact mode uses Hyndman–Fan type 7 rank `h=(n-1)p` and exact linear interpolation over ordered values, preserving exact integer/Decimal inputs and the declared output precision. Exact computation is the default and unsupported backend/type combinations refuse.
- Approximation is a separate explicit request, `approx_quantile(metric: str, probability: Decimal | str, *, window: tuple[str, str], sketch: SketchRequest) -> ApproxMetricQuantile`, never a hidden fallback from `quantile`. `SketchRequest` names a supported algorithm/version and its rank-error guarantee; unsupported/uninstalled sketch requests refuse before query. The chosen package/algorithm remains owner-gated.
- Nonadditive expression binding resolves a declared metric to a typed operation carrying `exactness: Literal["exact","approximate"]`, algorithm/version where approximate, approximation guarantee, merge semantics, and any required ordering policy. Numeric bounds and exactness are metadata, not statistical uncertainty.
- Optional sketch API stays module-scoped: mergeable sketches support merge/estimate/error metadata but not prefix subtraction; uninstalled/unsupported sketch requests raise the stable metric refusal before query execution. Do not export sketch implementation classes from root.
- Retention threshold bands are based on independent event-occurrence references, an explicit target event, threshold semantics, declared horizon (`finite` or `open_ended`), and source completeness. A band is not computed by summing distinct counts or by treating missing horizon as retention failure.
- Runtime estimates distinguish forecast, verified upper bound, and backend-enforced cap plus evidence/basis. Strict `Budget.max_scan_bytes` authorization requires a sufficient bound/cap for every source-read phase (capture, validation/integrity, execution, retries); estimates alone cannot authorize a strict limit. Preserve all phases as separate scan work.
- Cost/task schema changes live with Task 5 below: add or preserve scan/output/row estimate fields, canonical serialization, version and fingerprint behavior in one place. If Task 7.1 already landed these fields, extend the existing record without duplicate fields; if not, make the compatible schema/version change and test old-plan handling there.
- Fitted winsor limits are typed immutable training-transform artifacts persisted with the training/scoring recipe, threshold method/version, fit population/snapshot/split identity, and typed thresholds. A fresh process can load/apply the frozen artifact without original training rows or refitting; fitting requires Task 7.2's declared training view/split boundary.
- Scalable synthetic generation is deterministic by seed and generation version; exposes bounded batches/chunks without a whole-world intermediate and separates visible observations from oracle/truth data. Benchmark records distinguish observed from unavailable metrics.

No provider, account, size or maximum spend is specified. Recommendation: select one existing supported target among PostgreSQL, Snowflake or BigQuery with explicit dataset scale, execution/spend ceilings, credentials path and cancellation expectation before authorizing the live integration. Until then implement test harness and DuckDB evidence only; mark live support unverified.
- **Owner gate — optional sketch licensing/release:** A concrete optional mergeable sketch implementation/package and license are not named. Recommendation: prefer a compatible, maintained implementation only after reviewing license, version, exact algorithm/error and deterministic merge guarantees; otherwise expose no sketch implementation and return a coded refusal while shipping exact bounded modes. Do not vendor, license or distribute a dependency by inference.
- **Recommendation — no universal scale promise:** Set workload sizes from a measured local calibration and owner-approved live limit. Avoid advertised billion-event support or fixed overhead percentages until evidence measures that workload/backend.

## Spec Contradictions / Clarifications

- Roadmap 8.1 requires a quantile capability but leaves quantile convention and probability input unspecified. This plan resolves that gap with exact Hyndman–Fan type 7 quantiles requested through `quantile(...)` by default, canonical Decimal probability, and a separate explicit approximate-sketch request. Backend/type support remains capability-matrix gated and unsupported cases refuse.
- “Exactness guarantees” for sketch-type metrics are internally ambiguous: a sketch is approximate unless a particular exact mode is demonstrated. This plan interprets as explicit algorithmic accuracy/error guarantees and exactness metadata; sketches never claim exact answers or prefix-subtraction compatibility.
- “Dry-run cost estimates and budgets on runtime plans” is a new Task 8.1 requirement, while Task 7.1's planner is metadata-only and DuckDB advertises no scan estimate. Task 5 distinguishes forecasts from verified upper bounds and enforceable caps; strict budgets require a sufficient bound/cap across every input-reading phase, and unknown remains a refusal rather than a hidden scan.
- Roadmap requests a “live-warehouse tier under integration/warehouse_execution/” but does not choose provider, target scale, or budget; the live harness is planned but its paid execution remains an explicit owner decision.
