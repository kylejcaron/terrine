# Terrine Backend and Common-Stack Interoperability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Terrine's dataset backend and common-stack support explicit, narrowly gated, and evidenced by real execution while keeping the caller's existing warehouse, file, dbt, dataframe, and semantic-definition workflows intact.

**Architecture:** Extend the existing `terrine.runtime.backends.base.BackendCapabilities` / `RuntimeBackend` contract and make each operation check its own proven capabilities; do not confuse Ibis SQL compilation with executed backend support. Reuse the existing `Model` → `Design` → `Frame` compiler, `Dataset` staging/export protocol, safe native `Catalog`, and dbt recipe; add only narrow bridges for existing stack inputs and conversions. Backend integrations remain optional and customer-owned, and a capability is advertised only after its live integration evidence passes.

**Tech Stack:** Python `>=3.13,<3.15` subject to Task 0.1 compatibility evidence; existing Ibis, PyArrow, DuckDB, pytest, pandas and Polars optional extras, dbt Core optional extra; PostgreSQL/Snowflake/BigQuery Ibis drivers isolated as backend extras. No cloud SDK or warehouse driver in the base install.

**Spec:** Roadmap Task 8.2 and “Common-stack integration contract” in `docs/superpowers/plans/2026-10-16-terrine-build.md`; binding datasets-only scope in `docs/superpowers/specs/2026-10-18-terrine-scope-datasets-only.md`; Task 7.1 runtime/backend contracts in `docs/superpowers/plans/2026-10-18-terrine-materialization-runtime.md`; Task 7.2 Dataset/Arrow/Parquet contracts in `docs/superpowers/plans/2026-10-18-terrine-ml-staging.md`; `AGENTS.md`.


## Scope ledger

- Dataset backend/runtime capability work, dataset construction, materialization and staging are authorized by the In scope line: “Anchors, windows, aggregates, as-of attributes, expansion, all frame shapes (cross-section, sequential/scheduled, calendar and event panels, cohorts, LTV, time-to-event, state panels, sequences), static temporal validation, null-not-zero censoring, coverage/readiness, materialization runtime, ML staging, orchestrators, dataset agent tools.”
- Arrow/Parquet ML hand-offs are authorized only as datasets: “sklearn / Arrow | Existing ML staging | Labeled datasets, not causal hand-offs”
- Spec integrations authorized verbatim by the table:
  - “| DoubleML | Recipe | `DoubleMLData(..., cluster_cols=...)` for repeated rows |”
  - “| DoWhy | Recipe | One-row-per-unit, unweighted frames only. `CausalModel` has no cluster or weight arguments (extra keywords are stored, not applied), so the recipe refuses repeated units and declared weights |”
  - “| duckreg | Recipe | Runs on the same Ibis connection against the materialized frame table; only compressed aggregates leave the warehouse, never rows |”
  - “| lifelines | Helper | Two contracts. Kaplan–Meier: per-unit time-to-event records map to `KaplanMeierFitter.fit(durations, event_observed, entry=..., weights=...)`. Cox: a dataframe with `duration_col`, `event_col`, `entry_col`, `weights_col`, `cluster_col`. The risk-set table converts to lifelines input only without delayed entry (lifelines' table conversion reads event and censor counts only); with delayed entry, use per-unit records |”
  - “| diff-diff | Helper | Derives `first_treat` (including never-treated encoding per diff-diff's convention). Document and test only Callaway–Sant'Anna, Sun–Abraham and event studies; never SynthDiD (owner guardrail) |”
  - “| sklearn / Arrow | Existing ML staging | Labeled datasets, not causal hand-offs |”
  - “| increment | Optional recipe | One integration among others; never a requirement |”
  Every hand-off applies this explicit preflight: “**Export preflight (new, shared by every hand-off).** Before any library hand-off: incomplete outcome windows are refused or dropped with excluded counts per exact reason (never zero-filled or imputed); unknown eligibility is refused; repeated rows per independent unit require a cluster column; grace-defined treatment is refused as a baseline treatment. Move these checks out of `terrine/estimate/_data.py` and `panel.py` rather than rewriting them. One refusal code per hazard, shared across entry points.”
- Named PostgreSQL, Snowflake and BigQuery services are not granted by the scope spec; owner-gated through kata `ak9y`, including credentials, paid queries and resource use.
- External object-store support is not explicitly authorized; owner-gated through kata `rrsf`. Named dbt Core integration is also not explicitly authorized by this scope decision and remains owner-gated.
- MetricFlow and LookML imports are unsupported absent an independently authorized, versioned, lossless mapping; do not infer compatibility from arbitrary YAML.
## Global Constraints

- terrine helps people and agents quickly and safely build well-constructed, point-in-time-correct datasets from source data.
- It is a standalone package: it must be fully useful with no relationship to increment. It makes no causal claims and ships no effect estimators.
- Each integration maps frame roles to the library's arguments on top of the export preflight. Start as documentation recipes; write a helper only where the mapping has a real gotcha.
- Unit tests MUST NOT use the network or a real warehouse. Live warehouse checks belong under `integration/warehouse_execution/`.
- Unsupported public requests raise a coded error with a stable package-wide code and immutable, structured context, before loading data or calculating results.
- A refusal MUST cover only the variant its reason applies to and MUST name a route forward when one exists.
- No data routed through hosted terrine services and no payload/secret logging. Credentials and connections are caller-side or environment/connection references; saved specs/manifests/tool responses never embed secrets.
- SQL is parsed/admitted using the dialect that will execute it; read-only safety is rejected when it cannot be established.
- Unknown scan work cannot satisfy a strict scan budget; output/file limits do not bound scan work.
- Execute a live integration before advertising an operation. Absent credentials leave an explicit unverified capability, never a fake success or compile-only support claim. Paid resources require owner-approved limits.
- Keep optional backend drivers/storage authentication out of local DuckDB usage; honor caller-provided filesystems and credential providers.
- Implement dataset construction/staging only. No estimators, causal mode, causal-library hand-offs, or inference behaviors are in scope.

## Review Focus

1. **An Ibis backend compiles SQL but does not honor one of Terrine's semantic guarantees:** pin each dialect/operation to actual typed-row parity or a pre-execution coded refusal in `tests/integration/warehouse_execution/test_backend_capabilities.py` and backend integration cases.
2. **A capability is unknown rather than false, or only one operation lacks support:** test unknown snapshot/cost/publication behavior separately from known support and prove ordinary read/materialize remains available when only staging/export refuses in `tests/runtime/test_backend_capabilities.py`.
3. **Timestamp equality, decimal overflow/scale, or null metadata changes during driver conversion:** test strict t0, SCD2 boundaries, overflow and round-trip metadata in the backend parity fixture and `tests/test_common_stack_interop.py`.
4. **A dbt manifest points to a different, unreviewed, ephemeral, or malformed relation:** test reviewed node identity and exact resolved relation binding before source reads in `tests/adapters/test_dbt_relations.py`.
5. **A conversion/export or semantic adapter drops role/precision/completeness meaning or guesses unsupported semantics:** test metadata-preserving Arrow/Polars/pandas/Parquet paths and narrow semantic refusal in `tests/test_common_stack_interop.py` and `tests/compat/test_semantic_interop.py`.

## File and Interface Map

- `terrine/execution/backend.py`: new execution-owned backend provider interface for connection/dialect identity, relation resolution/admission, and bounded caller-owned execution. `Model`, compiler and runtime may depend on this interface without importing `terrine.runtime`; it preserves DuckDB's current verified native path.
- `terrine/backends/capabilities.py`: pure, runtime-independent `BackendCapabilities` value and backend/capability resolution contract shared by compilation, execution and runtime. It imports neither runtime leases nor driver packages.
- `terrine/runtime/backends/base.py`: retain `RuntimeBackend`, `PublicationReceipt`, and staging receipt types; consume/re-export the shared capability value where appropriate, while keeping leases/publication protocols in runtime.
- `terrine/runtime/backends/duckdb.py`: declare only DuckDB facts actually supported by existing runtime transactions, snapshot, batch-read and export paths; do not weaken its tested atomic publication claims.
- `terrine/runtime/backends/{postgres,snowflake,bigquery}.py`: add a backend implementation only for capabilities actually exercised; otherwise leave the backend absent/unverified and use the capability refusal rather than a pass-through Ibis adapter.
- `terrine/runtime/backends/__init__.py`: deliberate exports, only if a backend class is implemented.
- `terrine/model.py`, `terrine/compile/anchors.py`, `terrine/compile/cost.py`, `terrine/runtime/planner.py`, `terrine/dataset/reference.py`, `terrine/dataset/export.py`: consume the execution-owned provider/shared capability contract at the relevant operation boundary. In build worktree where Dataset code is not yet present, coordinate this task's implementation dependency on the completed Task 7.2 merge; do not copy the separate ML-staging worktree implementation as a second API.
- `terrine/execution/_native.py`, `terrine/execution/inputs.py`: preserve native DuckDB verification and immutable-input behavior; route backend-neutral connection/relation operations through `terrine.execution.backend` rather than broadening DuckDB-only helpers.
- `pyproject.toml`: optional extras for verified backend drivers; pandas/Polars/dbt remain independently installable optional extras.
- `terrine/frame.py`, `terrine/data.py`: preserve current Frame conversions and `MaterializedFrame` Arrow metadata; changes only for a demonstrated interop defect.
- Existing `examples/orchestrators/dbt_core_after_build.py`: extend the existing dbt Core after-build recipe with reviewed manifest relation resolution and Dataset stage/refresh, without executing manifest code or dbt macros.
- `examples/dbt_dataset.py`: self-contained local dbt Core → reviewed manifest relation → native Catalog/Design/Frame/Dataset workflow.
- `examples/backend_interop.py`, `examples/common_stack_interop.py`: runnable local DuckDB + Arrow/Parquet and optional dataframe/dbt examples; no network by default.
- `docs/guides/backend-compatibility.md`: capability meanings, known/unknown/refused operation matrix, verified driver versions and execution evidence; document only what was tested.
- `docs/guides/common-stack-interop.md`: existing dbt/catalog and Arrow/Polars/pandas recipes, optional dependency behavior, schema/role/provenance limits, and semantic refusals.
- Tests: `tests/runtime/test_backend_capabilities.py`, `tests/test_common_stack_interop.py`, `tests/adapters/test_dbt_relations.py`, `tests/compat/test_semantic_interop.py`, and `tests/execution/test_backend_provider.py`: fast deterministic unit coverage.

- `tests/test_optional_dependencies.py`, `CHANGELOG.md`, `terrine/__init__.py`: preserve optional import isolation and publish user-visible changes/reviewed public APIs.
