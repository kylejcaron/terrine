# Terrine Orchestrator Adapters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add optional Airflow and Dagster adapters plus a dbt Core after-build recipe that trigger the authoritative Terrine materialization runtime without moving planning, state, idempotency, or fencing into an orchestrator.

**Architecture:** Adapters use owner-local `ControlClient` for canonical plan submission, run, status, event, cancellation, and destination-scoped request-key operations. Airflow/Dagster schedule a complete runtime plan; the runtime's dependency graph and fenced executor own intervals, dependencies, resource leases, publication, and durable status. Adapters persist stable invocation identities and replay exact owner receipts; a failed run resumes under a newer lease fence with its existing run ID, request key, and completed task outputs. Succeeded and cancelled runs are terminal. The dbt Core example runs after `dbt build`, binds reviewed dbt relations as sources, then calls the same plan/run path. Framework imports and dependencies stay isolated in optional extras.

**Tech Stack:** Python `>=3.13,<3.15`; existing Terrine runtime/ControlClient and local DuckDB owner; optional Apache Airflow and Dagster extras, dbt Core guide/recipe; pytest. Adapter tests use local DuckDB and in-process or local owner IPC only; no network or real warehouse.

**Spec:** `docs/superpowers/plans/2026-10-16-terrine-build.md` Task 9.1; `docs/superpowers/specs/2026-10-16-terrine-handoff.md` §§14–17; `docs/superpowers/plans/2026-10-18-terrine-materialization-runtime.md` (Task 7.1 runtime and its public API); runtime guide `docs/guides/materialization-runtime.md`; repository `AGENTS.md`.

## Global Constraints

- CLI and Python runtime remain authoritative; Airflow TaskGroup, Dagster partitioned assets, and the dbt Core after-build recipe are thin optional triggers.
- Scheduler payloads carry run/task IDs and bounded metadata only, never rows, credentials, raw SQL, source connection strings, or backend error text.
- For each logical scheduler invocation, submit an owner-side `PlanRequest` containing a stable invocation ID, verified `ModelReference`, canonical `Design`, destination, optional `ChangeSet`, and `Budget`. The owner resolves source revisions/snapshot and expected base manifest, runs preflight, creates and durably stores one `PlanInvocation`, and derives its destination-scoped request key. Repeated submissions of the same invocation ID return the same plan/key; retry of its failed run uses that same ID/key/run and resumes only under a newer runtime lease fence. A new logical invocation gets a new ID/key.
- Runtime resource leases and fencing protect overlapping runs and stale writers; adapters MUST NOT acquire, renew, release, or emulate leases.
- Task 7.1 MUST expose the owner-side planning/run/status/cancel/request-key operations over the existing owner IPC, with versioned request/response schemas, namespace authorization, idempotent plan submission, and status/cancel service concurrent with a blocking run. Existing `ControlClient.plan(serialized_plan)` only canonicalizes an already-built plan, so it is not sufficient for scheduler-side fresh planning; adapters MUST NOT build plans by opening the owner's DuckDB.
- Owner planning and persisted composition MUST use the same shared execution gate as `Frame._materialize`, route through `compile_design`'s enumerated supported-shape matrix, and refuse unsupported shape, unknown eligibility, or strict-budget violations before snapshot capture/source work. Snapshot capture is limited to the plan's source dependency closure. Dependency discovery includes nested selector sources and recursively selected measurement/as-of support; if exact selector support is unknown, rebuild conservatively.
- Task failures remain visible as failed runtime status until an explicit scheduler retry succeeds under a newer fence; adapters MUST NOT reclassify a failed result as success or emulate attempts/fences. Succeeded and cancelled runs are terminal and never regress. Empty runtime layers do not skip downstream work; scheduler success is not evidence of publication. Response-loss retries and failed-run recovery both replay the same persisted plan/key/run. A new logical invocation uses a new owner planning invocation and key.
- Cancellation is a durable request, not proof that backend work or billing stopped; stale status remains stale/unknown. Monitoring failures MUST NOT turn execution into success.
- Base Terrine installation MUST NOT import or require Airflow, Dagster, dbt Core, or provider packages. Declare exact tested compatibility ranges/pins only in independent optional extras and keep imports lazy at adapter boundaries.
- Airflow connection URIs are not assumed to be Ibis-compatible. The owner runtime owns its backend connection; only add a direct Airflow hook/backend mapping when that backend mapping is explicitly tested.
- dbt Cloud generated microbatch models are excluded by the adopted handoff default; this plan implements dbt Core's after-build recipe only.
- Unit and adapter integration tests use tiny deterministic fixtures and local DuckDB; no network/warehouse. Live backend capability claims remain outside this task.
- Public package facades keep reviewed explicit `__all__`; adapter APIs live in focused modules, not the everyday Model/Design/Frame/Dataset surface.

## Review Focus

1. A scheduler loses a planning/run response or retries a failed run: the same invocation ID returns the same owner-persisted plan/key/run, and failed work resumes only under a newer lease fence while reusing completed task outputs; test `test_lost_response_and_failed_run_retry_reuse_fenced_invocation` in Task 1. Succeeded/cancelled runs remain terminal; test `test_terminal_success_and_cancellation_never_regress` in Task 1.
2. A model/design/snapshot changes while an invocation ID or request key is reused: runtime refuses the conflict; a new logical invocation resolves a fresh snapshot/base manifest; tests `test_changed_plan_under_existing_invocation_id_refuses` and `test_new_invocation_resolves_current_snapshot` in Task 1.
3. An empty upstream layer has dependent work: the owner's whole-plan DAG still runs required downstream tasks; test `test_empty_layer_does_not_skip_downstream_runtime_work` in Task 2.
4. A requested shape fails shared eligibility/budget validation, or a nested selector changes: owner refuses before snapshot/source work or invalidates selector-dependent results for same-snapshot parity; test `test_shared_preflight_refuses_before_snapshot_and_selector_correction_matches_rebuild` in Task 3.
5. A Dagster historical partition is materialized or a local dbt build overlaps the DuckDB owner: each partition maps to a distinct pinned partition/snapshot output; dbt stops/restarts owner, and repeated builds use durable invocation IDs; tests `test_historical_partitions_pin_distinct_outputs` and `test_two_dbt_build_refresh_cycles_reacquire_owner_and_advance_snapshot` in Tasks 2 and 3.

## File and Interface Map

- `terrine/orchestration/__init__.py`: focused orchestration package marker with no optional imports or re-exports.
- `terrine/orchestration/airflow.py`: optional Airflow TaskGroup/operator boundary; uses owner-local plan/run/status/control and returns only run identifiers/metadata.

- `examples/orchestrators/airflow_materialization.py`, `examples/orchestrators/dagster_materialization.py`: runnable local DuckDB examples using the orchestration adapter APIs.
- `docs/guides/orchestrators.md`: owner-side planning setup, optional installs, scheduler configuration, dbt Core after-build lifecycle, retry/status/cancel semantics and limits.

## Open Decisions / Gates

- The handoff proposes per-layer Airflow mapping, but the runtime implementation exposes `ControlClient.plan/run` for whole-plan execution and no stable per-layer execution endpoint. Recommendation: keep the scheduler boundary at a whole plan and require local IPC tests proving concurrent status/cancel while run is active; do not invent parallel per-layer APIs.
- The roadmap says Airflow connections require a verified hook/backend mapping, while the materialization runtime guide assigns the connection to an owner process and exposes owner-local IPC. Recommendation: adapters use the owner endpoint and do not pass Airflow URI to Ibis; document and test backend connection ownership there. Add hook mappings only for separately capability-tested backends.
- **Runtime planning prerequisite:** Task 7.1 currently exposes `ControlClient.plan(serialized_plan)` as canonicalization for a caller-built `RefreshPlan`; `SavedPlanRecipe`/`resolve_plan` restore an already-snapshotted plan, not a fresh owner-side plan request. Task 9.1 cannot safely implement the roadmap's scheduler-triggered fresh planning until Task 7.1 extends the existing owner IPC plan operation to accept a versioned request with ModelReference, Design, destination, changes, budget, stable invocation ID and optional output scope, then owner-resolves source state, runs the shared preflight gate, captures only the dependency closure, and durably returns the identical `PlanInvocation` for replay. Recommendation: make this a Task 7.1 integration prerequisite, not a second transport or scheduler-side DuckDB path; add a separate-process local test proving this API and invocation record survive response loss/restart.
- **Failed-run retry contract:** the runtime integration must permit retrying a `failed` run with the same run ID/request key only under a newer lease fence, reusing completed task outputs while rejecting stale writers. `succeeded` and `cancelled` are terminal. This is the required Task 7.1 contract (not an adapter-owned attempt model); tests must verify fencing, publication parity and terminal-state preservation.
- **Durable dbt identity:** the current runtime does not document owner-persisted plan invocation lookup. A volatile helper cache cannot distinguish a fresh-process retry after owner restart from a new dbt build. Recommendation: persist the canonical plan/key/destination under the caller's stable `build_id` as the invocation ID as part of the owner planning prerequisite; every retry of that build reuses its ID, and a new dbt build must supply a new one.
- Exact tested Airflow, Dagster, and dbt Core/local-adapter compatibility pins are not named by Task 9.1. Recommendation: select and pin versions available to the isolated integration test environments, constrain only optional extras, and keep base install independent.
- **Release gate:** the roadmap forbids release before increment's public launch and the owner has not authorized publication. Recommendation: implement, test, and document locally only; request explicit owner authorization before any distribution release. No vendoring/licensing change is part of this task.

## Spec Contradictions Found

- `docs/superpowers/specs/2026-10-16-terrine-handoff.md` §14–15 describes per-layer dynamic mapped tasks, Airflow-side planner/lease operations, and `increment_semantic` module paths. Task 7.1's actual IPC provides whole-plan `ControlClient.run`, and `.plan(serialized_plan)` only canonicalizes a caller-built plan; it has no owner-side fresh planning request or independently runnable layer endpoint. The plan preserves whole-plan scheduling and marks owner-side planning as a prerequisite; runtime owns planning/leases.
- The roadmap says orchestrator jobs renew leases during queued/long-running work, while Task 7.1 centralizes resource leases and fencing in the runtime owner. Recommendation: owner owns queued lease renewal and fencing; adapters only trigger/cancel/status and never emulate leases. Airflow backend connections similarly remain owner-side; add a hook only for a separately capability-tested mapping.
- The handoff's dbt Core after-build example is silent about a local DuckDB owner's writer lock; the runtime guide forbids another process opening the writer-held file. The recipe therefore releases the owner before dbt build and restarts/reconciles before planning.
- The handoff mentions dbt Cloud microbatch generation/post-hook state writes, while Task 9.1 excludes dbt Cloud generated microbatch models by the adopted default. The plan includes only dbt Core after-build.
- The runtime implementation permits retrying a failed run with the same run ID under a newer fence, but the materialization runtime plan currently says terminal state never regresses. Resolved contract: failed runs are retryable with completed-output reuse; succeeded/cancelled runs are terminal. Task 7.1 documentation/tests must state this distinction consistently.
