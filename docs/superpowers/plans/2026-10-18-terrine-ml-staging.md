# Terrine Reproducible ML Dataset Staging and Streaming Exports Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stage immutable, reproducible ML datasets from Terrine Frames, assign leakage-safe deterministic evaluations, stream bounded Arrow/Parquet outputs, and refresh into new pinned generations.

**Architecture:** Keep Dataset as a lightweight reference to a customer-owned immutable output generation; persist a versioned canonical construction recipe and manifest beside generation/checksum records. Carry the full typed `DatasetRecipe`—including training/scoring view, selections and policies—through runtime plan reconstruction, task/output fingerprints, request replay and partition reuse. Reuse the existing Design/Frame compiler, metadata, and Task 7.1 retained-snapshot, lease/fencing, publication and recovery path; extend its task data boundary to stream bounded batches rather than making in-memory Arrow tables a prerequisite. Splits are a typed deterministic projection with explicit unassigned reasons, not a trainer or a second query compiler.

**Tech Stack:** Python `>=3.13,<3.15` target subject to Task 0.1 compatibility evidence; existing Ibis, PyArrow, DuckDB, Pydantic/data metadata and pytest stack. Arrow and Parquet are core staging formats; sklearn/PyTorch/XGBoost integrations are isolated optional extras and never required for staging or core imports.

**Spec:** Roadmap Task 7.2 in `docs/superpowers/plans/2026-10-16-terrine-build.md`; “Task 7.2 amendment: training views and scoring snapshots” in `docs/superpowers/plans/2026-10-16-terrine-dataset-workflows.md`; Task 7.1 contracts in `docs/superpowers/plans/2026-10-18-terrine-materialization-runtime.md`; runtime APIs in `terrine/runtime/{planner,execute,state,snapshot,recipe,backends/base,backends/duckdb,layers,api}.py` and `docs/guides/materialization-runtime.md`; current Frame/data/compile contracts in `terrine/{frame,data}.py`, `terrine/compile/`, `terrine/spec/`; repository `AGENTS.md`.

## Global Constraints

- Python target is `>=3.13,<3.15`, subject to Task 0.1 compatibility evidence; do not add trainer frameworks as core dependencies.
- `Dataset.to_arrow_batches` defaults to `batch_size=65536`; Parquet `target_file_bytes` defaults to `134217728` and is approximate. Validate positive limits and cap open writers.
- `Frame.stage(table: str, *, budget: Budget | None = None) -> Dataset` does not collect the Frame into Python. Bounded Arrow streaming and Parquet export are customer-owned and cancellation closes cursors.
- Preserve exact schema, integer/decimal precision policy, certificates/error-bound references, completeness and null reasons in the generation and its manifest/export metadata. Numeric nulls remain null with their reasons.
- A manifest includes dataset/generation IDs, design/model hashes, source coverage and authoritative snapshots or explicit unknown status, column types/roles/windows, label completeness, split policy, execution-measured row counts, partition/shard references and checksums, creation/schema/compiler versions, and the versioned canonical construction recipe or a verified immutable customer-owned recipe reference. Never store credentials, rows, raw SQL, live handles or executable code in it.
- Retain a reopenable immutable input snapshot for every partition/retry; an unknown upstream revision is not itself a missing snapshot. A successfully staged output is immutable and reusable even if its source revision is unknown, but refresh/reconstruction requiring source work refuses when coherent retained inputs cannot be reopened. Separate feature-definition identity from data/source-generation identity. A hash is not a reconstruction recipe.
- Time split boundaries are explicit ISO dates/aware instants, ordered, and embargo is nonnegative elapsed time. Group hashes use canonical typed string/integer keys and the exact `terrine.group.v1` SHA-256 codec and integer thresholds specified in the dataset-workflow amendment. Reject bool/null/unsupported keys; never stringify ambiguously.
- Forward-time assignment uses complete selected-label support before the next boundary; aggregate labels ending at the boundary may qualify, point-state labels require `to_time < boundary`. Purge overlapping label horizons, apply embargo between adjacent splits, and preserve `unassigned` reasons for unavailable/purged/mismatched rows. Do not assign by outcomes, treatment or future availability, shuffle to restore sizes, or fit preprocessing outside training rows.
- Same unit may occur in different time buckets for existing-user forecasting; unseen-unit evaluation additionally intersects deterministic disjoint group buckets. Train-only preprocessing remains the downstream consumer's responsibility; the split manifest must make those rows identifiable.
- Scoring snapshots are roster-backed, feature-only, cross-sectional Designs with explicit eligibility; they do not inherit historical event cohorts or require future outcomes/readiness. Resolve `"today"` once to the fixed Catalog-local day boundary, persist the UTC instant, and preserve that `as_of` across refresh.
- Keep measurement/effective-time versus recorded-at knowledge visible. Split safeguards do not establish historical availability and no bitemporal system is introduced.
- Generation-specific staging tables/export prefixes; publish manifest only after all partitions are durable and verified. Retry resumes only matching generation/partition/checksum under Task 7.1 fencing; never mix generations or destructively overwrite an existing user table/path. Partition by bounded date/hash buckets, never an unbounded per-unit partition scheme.
- `Budget.max_rows`, `max_output_bytes`, `max_scan_bytes`, and `strict_scan` remain distinct. Report source scans, output rows/bytes, export egress and client memory independently; output/file limits do not bound scan work. Unknown scan work cannot satisfy a strict scan budget. Do not collect the full output to enforce limits.
- Refresh planning is metadata-only apart from supported source-revision discovery. `None` changes means discover authoritative revision metadata, not assume append-only. A refresh returns a new pinned generation; copy-on-write reuse requires equivalent dependency fingerprints and recorded content identity. Readers of old generations remain valid; GC obeys explicit ownership, pins and retention.
- No network/warehouse in unit tests; backend execution belongs under `integration/warehouse_execution/`. Keep secrets and credentials client-side. No increment edits/dependency, hosted data, trainer dependency in core, or release/publishing authorization.
- Use explicit reviewed `__all__`, coded narrow refusals with a route forward, reuse the everyday Model/Design/Frame/Dataset workflow, and update owned docs/example/changelog with complete changes.

## Review Focus

1. **Output growth, writer fanout, or stalled cancellation:** memory must be bounded by configured Arrow batches and capped writers, and closing/cancelling must release the cursor. Test Task 3 `test_arrow_stream_memory_is_bounded_and_close_releases_reader`.
2. **Cutoff equality and labels with overlapping windows:** preserve aggregate half-open end equality versus point-label strict inequality and embargo/purge rules. Test Task 2 `test_time_split_purges_overlapping_labels_and_respects_point_vs_interval_equality`.
3. **Typed identifiers and repeat appearances:** integer `7` and string `"7"` never alias; repeated unit keys receive one group bucket regardless of order. Test Task 2 `test_group_split_typed_keys_are_order_independent_and_never_alias`.
4. **A retry or restatement while an old reader remains open:** verified output shards cannot cross generations and old references remain unchanged. Test Task 5 `test_refresh_publishes_new_generation_without_mutating_pinned_reader`.
5. **Untrusted/incomplete reconstruction recipes and missing source authority:** validate recipe digest/schema/owner before source work; retain a coherent reopenable input snapshot and preserve unknown upstream revision/readiness explicitly. Test Task 1 `test_dataset_recipe_refuses_corrupt_or_unsupported_content_before_source_access` and Task 3 `test_stage_refuses_when_retained_snapshot_cannot_be_reopened`.

## Interfaces and Runtime Boundary

Use the roadmap public signatures without parallel aliases:

```python
Frame.stage(table: str, *, budget: Budget | None = None) -> Dataset
Dataset.to_arrow_batches(*, batch_size: int = 65536) -> Iterator[pyarrow.RecordBatch]
Dataset.export_parquet(
    *, destination: str, partition_by: tuple[str, ...] = (),
    target_file_bytes: int = 134217728, budget: Budget | None = None,
) -> ExportManifest
Dataset.plan_refresh(
    model: Model, *, changes: ChangeSet | None = None,
    budget: Budget | None = None,
) -> RefreshPlan
Dataset.refresh(
    model: Model, *, changes: ChangeSet | None = None,
    budget: Budget | None = None,
) -> Dataset
Dataset.from_manifest(manifest: DatasetManifest, *, con) -> Dataset
```

The amendment additionally owns `Frame.training_set(...)`, `Design.snapshot(...)`, typed `TimeSplit`/`GroupSplit`, `DatasetViewMeta`, and `DatasetRecipe(schema_version=1, base_design, view=None)`; implement the exact signatures and split/reconstruction contracts in the cited amendment, not a second variant here. Training/scoring views reuse the same staging/refresh flow. `Dataset.from_manifest` only resolves verified owner-configured references and the exact committed output generation; no arbitrary URLs.

Task 7.1's existing boundary is real and must be reused: `plan_refresh(...) -> RefreshPlan`, `TaskSpec`, `run_plan(...) -> RunReceipt`, `open_published_generation(receipt, ...)`, `RuntimeStore`, `SnapshotAuthority`, `DuckDBBackend.publish_generation(...)`, compiler-owned `LayerKey` substitutions through `compile_design`, and leases/fencing. Persist the complete DatasetRecipe or verified immutable recipe reference, including `view_hash`, in the runtime's versioned PlanRecipe; it must survive fresh-process reconstruction and participate in task identities, output fingerprints, partition-reuse decisions and destination-scoped request-key replay. The same Design with a different selected view must have different execution identity and cannot replay or reuse incompatible partitions. Refresh translates its recipe/model/manifest and supported `ChangeSet` into that path, supplies the owner executor, and uses the retained reopenable snapshot for all tasks/retries; no direct manifest/table mutation. Keep credentials in caller/owner context, not recipe or plan JSON.

## Open Decisions / Gates

- The master roadmap requires one supported customer-owned object-store/warehouse export integration before advertising that support, but does not select a provider/backend or guarantee credentials are available. **Recommendation:** implement and verify the local DuckDB/Parquet path first; record the provider and actual backend capability in implementation evidence, and claim cloud/warehouse support only after that specific integration passes. If credentials or a supported provider are unavailable, leave that advertised integration gate open rather than substituting a mock.
- The default `Frame.stage` path is synchronous DuckDB, but its public signature has no explicit runtime namespace/owner argument. **Recommendation:** derive `RuntimeOwner.state_path` from the caller-owned file-backed DuckDB connection, resolve `snapshot_root` from `TERRINE_RUNTIME_SNAPSHOT_ROOT` or `<database-parent>/.terrine/snapshots`, and resolve namespace from `TERRINE_RUNTIME_NAMESPACE` or `terrine_runtime`. Refuse non-file-backed connections without explicit owner-compatible durable storage; keep owner-provided executors for explicit asynchronous/non-default-backend work. Do not require users to author task callbacks for ordinary staging.
- Roadmap/API examples include object storage and optional framework consumers but do not name a specific trainer library or promise framework-specific loader APIs. **Recommendation:** implement Arrow/Parquet as the required interop surface; add only thin loader adapters for frameworks actually selected and exercised, each isolated behind its own extra. No loader dependency or trainer integration becomes core.

## Spec Contradictions / Reconciliation

- Task 7.2 requires bounded batch streaming, Parquet shards, checksums, resumability and client-memory bounds, while current runtime `StagedGeneration` is an in-memory mapping of `pa.Table` and DuckDB `read_partition` materializes a full table. Resolved in this plan by explicitly extending the same Task 7.1 runtime boundary to bounded streams/immutable staged refs before calling it compliant; no parallel staging runtime is introduced.
- Roadmap allows source revision identity to be unknown while requiring a staged output to be immutable; Task 7.1 separately requires retained, reopenable immutable inputs for partitions/retries. An unknown upstream revision is compatible with a retained snapshot receipt, but does not establish source-change detection. Task 3 preserves these as distinct facts and refuses refresh/staging work when coherent inputs cannot be retained or reopened.
- Master roadmap calls the store/export destination customer-owned and warns that object-storage support cannot be inferred from URI acceptance. Runtime publication currently proves DuckDB transactional table/manifest publication, not external object-store atomicity. Task 4 therefore publishes external shard manifests only through an implemented, verified storage publication protocol and does not generalize DuckDB atomicity to cloud backends.
