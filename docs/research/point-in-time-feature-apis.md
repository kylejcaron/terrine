# Point-in-time / cutoff-time feature APIs

## TL;DR

- Most systems make the observation timeline explicit: Featuretools accepts per-row `cutoff_time`; Compose searches label windows to emit cutoff rows; Chronon and Tecton use left/event timestamps or request time; Feast/Hopsworks use timestamped entity/label spines.
- Window names are not enough to establish boundary semantics. Featuretools documents inclusive cutoff by default and an `include_cutoff_time` switch; Chronon’s streaming example spells out `(t−W, t]`; several others leave exact equality behavior unspecified in the referenced API docs.
- Event time (`when it happened`) is distinct from availability/creation time (`when the system knew it`). Feast explicitly supports filtering by `created_timestamp`; ordinary event-time PIT can otherwise include a correction created later.
- “Late data” is not synonymous with “as-known-at”: watermarks govern stream processing/completeness, while true historical reproducibility requires ingestion/availability time or versioned snapshots and a cutoff on that second axis.
- Featuretools’ `approximate` batches costly calculations for nearby cutoffs; Chronon’s sawtooth windows combine fixed hops and a fresh tail; Tecton offers continuous event storage or partial aggregates. These solve serving/backfill cost differently from terrine’s planned prefix-sum lookups.
- Compose is especially relevant for outcome/label construction: `LabelMaker` has a target index, time index, labeling function(s), and future `window_size`; search supplies `minimum_data`, `maximum_data`, `gap`, and examples per instance.
- For terrine, retain explicit `(unit_id, anchor_id, t0)` plus interval-valued windows. Specify `[a,b)` once across primitives; separately model event-time, availability-time, and source completeness/watermark.

## API shapes and semantics

### Cutoff / anchor as an input relation

Featuretools and modern feature stores treat the anchor as row data, not merely a global date. Featuretools’ cutoff dataframe maps each instance id to its own calculation time and permits repeated entities at different cutoffs. Feast’s entity dataframe and Hopsworks’ label feature group play the same spine role. Chronon makes the timeline explicit in `Join.left` through a source `time_column`; an entity source instead yields midnight-granularity snapshots. These are strong precedents for terrine’s canonical anchor relation `(unit_id, anchor_id, t0)`, rather than implicit time inferred from whichever feature table is queried.

Compose approaches the same issue from the label side: target identity and time index are declared on `LabelMaker`, and `search` generates labels at chosen times. Its time window is outcome-forward, while feature calculation is delegated to Featuretools after generation. This separation is useful: terrine should keep anchor construction independent from role-specific feature/outcome windows.

### Relative windows and endpoint contracts

The systems expose a mix of durations and interval operators: Featuretools uses `training_window` relative to cutoff; Compose uses a future `window_size` plus a separate cadence `gap`; Chronon uses `Window(length, timeUnit)`; Feast uses TTL as a backward bound; Tecton uses a trailing `time_window`; Activity Schema uses relation names instead of explicit durations. Avoid importing another system’s boundary behavior silently. Featuretools explicitly includes the cutoff by default and can exclude it; Chronon gives a precise millisecond example; the rest of the sources inspected here do not settle exact same-time equality in their public pages.

Terrine’s uniform half-open interval `[a,b)` avoids adjacent-window double-counting: e.g. `[−7d,0)` excludes t0 and `[0,7d)` starts at t0 but not at the next window’s end. Apply this consistently to event predicates and prefix-sum subtraction; document timestamp precision and tie rules. This is terrine’s spec, not a claim that the comparison tools all use `[a,b)`.

## Late-arriving data: three different questions

1. **What happened? (event time)** Event timestamps determine which window an observation belongs to. Chronon, Feast, Tecton, and Hopsworks all use event-time/timeline joins for historical values. But event time alone cannot say whether a late record was actually available at historical prediction time.
2. **When did we know it? (availability / ingestion time)** Feast makes this distinction unusually explicit: `created_timestamp` both breaks ties among records with the same event timestamp and, only when opted in, filters out versions created after an anchor. Without that filter, event-time-correct joins can still expose retroactive corrections. For reproducible “as-known-at t0,” terrine should represent an availability/recorded-time axis in addition to validity/event time (or consume immutable source snapshots), and require `available_at <= t0` when that mode is requested. This is bitemporal semantics; do not equate a valid-time as-of lookup with an as-known-at lookup.
3. **How complete is the source? (watermark / data delay)** Tecton’s `watermark_delay_threshold` is an operational late/out-of-order allowance for streaming state. Larger thresholds avoid discarding events later but require more state. Chronon distinguishes temporal/realtime from snapshot/midnight feature accuracy and describes mutation-driven incremental updates plus asynchronous correction. These are important freshness/completeness policies, but neither by itself guarantees historical replay of what the online model knew at an old timestamp.

A robust terrine frame should therefore keep separate metadata: `t0` (anchor), requested event-time window, `available_at`/system-time cutoff when known-at reproducibility is requested, and source `data_end` / watermark / `observed_until` for censoring and completeness. Keep late-data policy explicit: (a) current corrected “as-of event time” view, (b) historical “as-known-at” view, or (c) snapshot/versioned source. For incomplete outcome windows, preserve censoring/nulls rather than silently zero-fill; the handoff spec already sets `observed_until = min(t0 + window_end, data_end, exit_date)`.

## Efficient window aggregation patterns

- **Chronon sawtooth:** fixed hopping buckets cover most of each trailing window, with a small sliding tail through the current event time. It avoids storing all raw events yet does not lose freshness at the bucket boundary. Useful precedent if terrine needs serving-oriented incremental views; it is not identical to exact warehouse historical prefix sums.
- **Tecton sliding vs continuous:** sliding partial aggregates bound read rows by `time_window / aggregation_interval` (often fewer for sparse entities), while continuous mode retains raw projected events and aggregates at request time, trading storage/read cost for freshness. Clarifies the cost/freshness axis and why aggregation interval is a visible operational parameter.
- **Featuretools approximation:** bucket nearby cutoff times and reuse costly feature calculations. This is an explicit compute/performance approximation; do not mistake it for exact feature values at each distinct t0.
- **Terrine planned approach:** additive metric windows can use per-unit cumulative values and two as-of point lookups: `C(t0+b) − C(t0+a)`. This is the handoff’s stated strategy and avoids anchor × window range joins. Non-additive metrics require rollups, mergeable sketches, or raw-event paths; corrections require invalidating/rebuilding affected cumulative suffixes or maintaining delta-aware histories. Prefix sums can support exact windows but only against a clearly selected data version/system-time snapshot.

## Implications for terrine

- **Adopt:** anchor dataframe as first-class input, matching Featuretools cutoff dataframes, Feast entity dataframes, and Chronon `Join.left`; retain stable `anchor_id` so repeated trials remain distinct.
- **Adopt:** a `Window(start, end, grain)` value with one public half-open contract `[a,b)`. Name `gap`, `grace`, `lookback`, and `horizon` as window values/aliases rather than subtly different operators.
- **Borrow names carefully:** `cutoff_time` is well-known but `t0`/`Anchor` is clearer with sequential trials; `training_window` means lookback in Featuretools, while Compose `window_size` means label-forward slice. Prefer terrine `Window` to avoid overloaded meanings.
- **Add an explicit availability axis:** feature/event source valid-time plus `available_at` (or ingestion/system-time) enables Feast-like `filter_by_created_timestamp` semantics. Distinguish `asof(attribute, offset)` on valid-time history from `as_known(attribute, t0)` if there are bitemporal corrections.
- **Expose completeness separately from point-in-time correctness:** per-source `data_end`/watermark and `observed_until` govern censoring; watermarks are not a substitute for as-known-at auditability.
- **Use corrections with care:** mutation-aware reversible aggregates can update sums/counts cheaply; max/min/other non-reversible states need recompute or retained candidate state. For persistent historical reproducibility, preserve versions rather than only eventual corrected state.
- **Avoid:** silently treating “event time ≤ cutoff” as “the value was available at cutoff”; silently treating same-time rows as inclusive; averaging features computed at approximate/bucketed cutoffs into supposedly exact study frames; anchor-by-window raw range joins at warehouse scale.
